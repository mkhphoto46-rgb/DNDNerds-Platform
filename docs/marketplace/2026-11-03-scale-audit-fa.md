# ممیزی مارکت‌پلیس برای تعداد زیاد خریدار — ۱۴۰۵/۸/۱۲

## نتیجهٔ تصمیم

انتشار کاتالوگ و آماده‌سازی فروشنده با فعال‌بودن کنترل‌های فعلی قابل تفکیک از راه‌اندازی خرید واقعی است. **فعال‌سازی خرید/پرداخت عمومی در وضعیت این ممیزی توصیه نمی‌شود:** خطای هم‌زمانی در لغو/انقضا/ثبت پرداخت بازتولید شد. افزایش RAM یا تعداد worker این خطا را درمان نمی‌کند و می‌تواند احتمال برخورد درخواست‌ها را بیشتر کند. UI جدید آبی/فیروزه‌ای/طلایی مبناست؛ این بررسی تغییری در طراحی ایجاد نکرد.

مبنای بررسی کد `d72e074` است؛ hotfix ادمین `12ea76c` سپس به‌صورت مستقل روی baseline فعلی تولید منتشر شد. کاتالوگ/لغو/پرداخت در این hotfix تغییر نکردند. کل HEAD توسعه روی تولید منتشر نشده و migrationهای0036/0037 هنوز جزو انتشار این hotfix نیستند.

## آنچه واقعاً اجرا شد

- PostgreSQL18 و Redis در کانتینرهای اختصاصی QA روی loopback؛ تست‌ها دیتابیس تصادفی خودشان را ساختند؛ دو artifact دیتابیس QA پس از ابزارهای CLI باقی ماندند و به دادهٔ توسعه/تولید دست زده نشد. هیچ بار خرید/پرداخت به تولید، PSP واقعی یا کاربران واقعی وارد نشد.
- چهار فایل تست موجود مارکت‌پلیس: **۲۱ پاس، صفر شکست**؛ شامل رقابت۱۰۰تایی آخرین SKU، سقف ریسک، ظرفیت ساخت، بازپرداخت جزئی، delivery review و replay.
- سپس پنج آزمون خصمانهٔ جدید، با قفل کنترل‌شدهٔ SQL برای تحمیل ترتیب برخورد، اجرا شدند. این‌ها عمداً invariant مطلوب را assert می‌کنند و در نسخهٔ معیوب باید قرمز بمانند؛ فایل `.audit.ts` برای اجرای صریح است و جزو تست‌های معمول نیست.
- کاتالوگ: ۳۰ فروشگاه،۳۰۰۰ محصول،۹۰۹۷تنوع،۱۰هزار حساب ساختگی،۵۰هزار زیرسفارش تاریخچه؛۶۰۰محصول ساختنی و۱۸۹۷بازهٔ ساخت؛۱۰هزار فیلتر ترکیبی فارسی/رنگ/موجودی. بار HTTP واقعی روی API؛ ۵۰اتصال/۶۰۰ثانیه سپس۲۰۰اتصال/۱۲۰ثانیه.
- محدودیت per-IP فقط داخل فرایند benchmark بالا برده شد؛ این موضوع عمداً در گزارش ثبت شده است. آزمون مستقل با محدودیت پیش‌فرض نیز اجرا شد و ایراد مسیر مشترک SSR را نشان داد.
- ماشین آزمایش Windows،Node24،۱۲پردازندهٔ منطقی و حدود۳۴GBحافظهٔ میزبان است. API و generator روی همان میزبان بودند. بخشی از مرحله۵۰اتصال هم‌زمان با build لینوکس و تست محدود hotfix ادمین بود؛ منابع میزبان اختصاصی نبودند. این اندازه‌گیری، گواه ظرفیت VPS یا بار ترکیبی Voice/VTT نیست.

## مواردی که از بررسی کد باید اصلاح شوند

جزئیات مسیر/خط و تفاوت «باگ»، «نیازمندی اجرا‌نشده» و «اثبات‌نشده» در `2026-11-03-spec-audit.md` آمده است. اولویت کاربردی:

1. **بازیابی خرید:** پرداخت ناموفق، refresh صفحه و پاسخ گم‌شده نباید سفارش رزروشده را بی‌راه ادامه رها کند. کلید idempotency و شناسهٔ سفارش تا نتیجهٔ قطعی پایدار بمانند؛ دکمهٔ ادامهٔ پرداخت در جزئیات سفارش و refresh پیش‌فاکتور منقضی اضافه شود.
2. **صفحه‌بندی واقعی:** سقف۱۰۰سفارش/۲۰۰محصول پنل و۶۰محصول صفحهٔ فروشگاه بدون ادامه، کار عملیاتی را پنهان می‌کند. cursor پایدار، فیلتر وضعیت و count معتبر لازم است؛ با۲۰۱محصول و۱۰۱سفارش معوق acceptance نوشته شود.
3. **فایل‌ها:** سقف جهانی۳۵۰MB و۲۰فایل برای هر حساب، ذخیرهٔ base64 درDB، قفل سراسری آپلود و نبود retention، برای پایلوت محدود است. رسانهٔ عمومی محصول از مرجع خصوصی جدا شود؛ object storage، cache محتوای immutable، lifecycle و سهمیهٔ اتمیک جایگزین شود. مرجع خصوصی هرگز صرفاً برای سرعت عمومی نشود.
4. **مقیاس query:** `count(*) over()`/OFFSET، شمارش exposure و محاسبات dashboard با دادهٔ رشد‌یافته EXPLAIN ANALYZE شوند؛ ایندکس‌هایی وجود دارند، پس ادعای «هیچ ایندکسی نیست» درست نیست. افزایش pool۱۰اتصالی بدون اندازه‌گیری راه‌حل قطعی نیست.
5. **پوشش اسپک:** قرارداد نسخه‌دار فروشنده، snapshot کامل سیاست/اصالت، اعتراض و hold دقیق، نگهداری/حذف شواهد، اعلان‌های بیرونی واقعی و اجرای واقعی تسویه هنوز نباید Done نامیده شوند. Gateهای PSP/KYC/حمل نیز جداگانه نیازمند شواهدند.

## راه عملی پیدا کردن باگ‌ها قبل از رشد

### لایه۱ — invariant به‌جای صرفاً پاسخ۲۰۰

پس از هر سناریو ازDB مستقل بخوانیم: `reserved=sum(ACTIVE reservations)`؛ موجودی و ظرفیت منفی نشوند؛ مجموع posting هر journal صفر؛ refund از captured بیشتر نشود؛ یک provider reference دوبار تخصیص نگیرد؛ orderموفق بالغوشده ناسازگار نماند؛ outbox منطقیِ پرداخت یک‌بار باشد. یک ledger متوازن به‌تنهایی تضمین نمی‌کند وضعیت سفارش یا رزرو درست است.

### لایه۲ — ترتیب‌های بد را عمداً تحمیل کنیم

ماتریس cancel×capture، cancel×expiry، capture×expiry، retry-intent×callback، quote-edit×accept، refund×shipment، policy-revoke×release نوشته شود. از barrier و SQL lock استفاده کنیم، نه sleep تصادفی و تکرار کور. ترتیب هر دوطرف اجرا و نتیجهٔ قابل‌قبول دقیق تعریف شود. تست‌های جدید این ممیزی ثابت کردند مسیر سبز عادی می‌تواندپاس باشد ولی ترکیب دو مسیر داده را خراب کند.

### لایه۳ — بار واقعی مسیر مشتری

پروفایل‌ها را جدا گزارش کنیم: مهمانSSR، مرور باعکس، خریدارواردشده، preview، ساخت‌سفارش، پرداختsandbox، وبهوک، پنل‌فروشنده و worker. تعداد حساب ذخیره‌شده مساوی خریدار هم‌زمان نیست؛ اتصال HTTP نیز مساوی سفارش‌درثانیه نیست. کنار closed-loop فعلی، fixed-arrival-rate اجرا شود تا کندشدن سرور نرخ تولید بار را خودبه‌خود پایین نیاورد؛ مرجع: https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/ .

### لایه۴ — بار نزدیک تولید و شکست سرویس

روی staging با بودجهٔ CPU/RAM/دیسک مشابه Tadserver، بارcatalog+checkout+worker و سپس Voice/VTTساختگی اجرا شود. ماتریس قطعRedis، restartAPIبعدازcommit، timeoutبعدازوصول، callbackدیررس/تکراری/جابجا، diskpressure و backlogاعلان اجرا شود. chaos فقط روی منابع اختصاصی staging، با stop condition و artifactقابل‌بازیابی. تست۱۲دقیقه‌ای API جای این مرحله را نمی‌گیرد.

### لایه۵ — دروازهٔ انتشار

هدف اولیهٔ خود اسپک برای API معمول p95<500ms است. برای عملیاتی‌کردن، خطای زیرساختی/timeout، درخواست‌های business-reject،429 و invariant جدا حساب شوند. شرط قطعی: صفر خطای مالی/موجودی حتی زیر فشار؛ query/pool/outbox بدون backlog فزاینده؛ بازیابی پس از افت بار؛ backupباrestoreتازه. ظرفیت اعلامی از rate ثابت پایدار و حاشیهٔ منابع همان staging به دست آید، نه از تعداد۱۲هزار حساب یا یک benchmark لپ‌تاپ.

## اجرای دوبارهٔ ابزارها

در `apps/api`، فقط PostgreSQL/Redis اختصاصی loopback را تنظیم کنید. مثال این اجرا: `TEST_POSTGRES_ADMIN_URL=postgres://postgres@127.0.0.1:15497/postgres` و Redisدرپورت6397 با DBاختصاصی؛ این نشانی‌ها تستی و بدون دادهٔ تولید بودند.

- بارخواندن: `node --import tsx dev/marketplace-scale-audit.ts`؛ `MARKETPLACE_LOAD_REPORT` مسیرartifactرا تعیین می‌کند.
